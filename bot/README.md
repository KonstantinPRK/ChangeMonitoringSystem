# Bot: команды и адаптеры мессенджеров

Модуль содержит общую логику команд и расширяемую инфраструктурную границу
для Telegram и VK. Реальные HTTP-клиенты платформ и постоянный цикл запуска
пока не реализованы.

## Ответственность компонентов

- `UserCommand` задаёт действие и стабильный код (`track`, `help` и т. д.).
- `CommandCatalog` описывает доступные команды. `DefaultCommandCatalog`
  сохраняет порядок справки и находит команду по коду.
- `CommandDispatcher` выбирает обработчик. Карта собирается через stream;
  дубликаты и отсутствие обработчика команды из каталога обнаруживаются при сборке.
- `CommandHandler` выполняет команду и возвращает текст.
- `MessengerAdapter` объединяет каталог, источник входящих сообщений и отправитель
  ответов одной платформы.
- `BotConfiguration` принимает коллекцию адаптеров и через stream создаёт интеграцию
  для каждого `MessengerType`. При добавлении платформы конфигурацию команд менять не нужно.
- `MessengerIntegration` обрабатывает команды и обычный текст. `pollOnce` получает
  сообщения из адаптера, а `process` позволяет будущему webhook передать сообщение напрямую.
- `TelegramMessengerAdapter` и `VkMessengerAdapter` изолируют правила своих платформ.

У Telegram имена для справки имеют вид `/track`, у VK сейчас — `track`.
В обоих случаях внутрь прикладной части передаётся код `track`, без префикса.
Исходный текст сообщения сохраняется отдельно: он потребуется для ссылок, тегов
и фильтров в продолжении диалога. Кнопки можно будет преобразовывать в тот же код
внутри адаптера VK.

`SubscriberId` обозначает получателя подписок в выбранном мессенджере.
Для текущего сценария это адрес личного диалога, известный адаптеру платформы;
это не универсальный идентификатор автора сообщения в группе. Одинаковые
`platformId` в Telegram и VK относятся к разным подписчикам.

## Подключение

При сборке приложения передаются `TrackerClient` и платформенные адаптеры:

```java
BotConfiguration configuration = new BotConfiguration(
    trackerClient,
    List.of(
        new TelegramMessengerAdapter(telegramApiClient, "ChangeDetectionBot"),
        new VkMessengerAdapter(vkApiClient)
    )
);
MessengerIntegration telegram = configuration.integration(MessengerType.TELEGRAM);

String reply = telegram.handleCommand(
    new SubscriberId(MessengerType.TELEGRAM, "123456789"),
    "help"
);
```

`TelegramApiClient` и `VkApiClient` — внедряемые транспортные интерфейсы. Они
задают операции получения и отправки уже отобранных личных текстовых сообщений,
но сами не выполняют HTTP-запросы. Поэтому наличие адаптеров ещё не означает,
что приложение подключено к Telegram или VK.

Чтобы добавить мессенджер, нужны:

1. Новое значение `MessengerType`.
2. Его транспортный клиент и DTO входящего сообщения.
3. Реализации `MessageUpdateSource` и `MessageSender`.
4. Класс `MessengerAdapter`, объединяющий эти компоненты и каталог.
5. Регистрация адаптера в коллекции при создании `BotConfiguration`.

Обработчики `START`, `TRACK`, `UNTRACK` и `LIST` при этом переиспользуются.
Отдельный `HelpCommandHandler` создаётся с каталогом конкретной платформы.

`TrackerClient` пока является прикладным интерфейсом регистрации и получения
списка ссылок; это не реализация HTTP-клиента и не описание сетевого протокола tracker.
Повторную регистрацию без дубликатов должна обеспечивать его реализация.

`START` вызывает регистрацию, `HELP` формирует справку, `LIST` получает ссылки.
`TRACK` и `UNTRACK` устанавливают состояние ожидания ссылки и возвращают приглашение.
Обработка следующего текстового сообщения, накопление ссылки/тегов/фильтров,
сохранение и удаление подписок, уведомления и обработка транспортных ошибок
относятся к следующим этапам. Состояния диалогов сейчас хранятся в памяти.

## Проверка

Из корня проекта:

```sh
./mvnw -pl bot -am test
```

Тесты используют локальные реализации транспортных интерфейсов и не обращаются
к Telegram, VK или tracker. Они проверяют разбор команд, сохранение обычного текста,
правильную платформу адресата и совместную работу адаптеров с общей логикой.
